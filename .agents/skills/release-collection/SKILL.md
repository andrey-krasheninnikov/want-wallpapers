# Выпуск коллекции Want Wallpapers

Работайте в `andrey-krasheninnikov/want-wallpapers`. Вход — URL папки `https://want-foundation.s3.twcstorage.ru/wallpapers/assets/collections/<number-and-name>/`. Явный вызов `$release-collection` с URL или запрос «добавь и выпусти коллекцию» разрешает подготовку данных, запись новых документов Firestore, публикацию веток, PR, merges, тега, GitHub Release и удаление соответствующих временных веток. Запрос изучения папки разрешает только чтение. Деплой Hosting требует отдельного запроса. Для коллекций этот порядок имеет приоритет над `release-feature`.

## 1. Подготовка

- Прочитайте применимые `AGENTS.md`, README и ADR каталога. Загрузите `$git-workflow-and-versioning` и `$delivery-commit-publish`; `$delivery-semantic-merge` загрузите перед обратным merge.
- Проверьте checkout, upstream, remotes, worktrees и активные Git-операции. При dirty checkout, detached HEAD или divergence остановитесь, сохранив пользовательские изменения.
- Выполните `git fetch --all --prune`; локальное отставание исправляйте только через `--ff-only`. Зафиксируйте через `git ls-remote` SHA `development`, `main`, целевых веток и тегов. До каждого merge сверяйте исходный и целевой SHA; изменившийся кандидат требует повторной проверки.
- Проверьте правила GitHub: `main`/`development` запрещают удаление и force-push, `release/v*` запрещает force-push и разрешает удаление, `v*` запрещает обновление и удаление тегов. Bypass отсутствует. Если правила мешают workflow, сообщите конкретный конфликт; не меняйте их и не обходите защиту без отдельного разрешения.
- Проверьте существующие документы, PR, ветки, тег и Release. При повторе используйте подтверждённые этапы по разделу «Возобновление».
- Для нового выпуска прочитайте `origin/main:package.json`. Требуйте стабильную версию `MAJOR.MINOR.PATCH`, согласованную с последним по SemVer стабильным `v*` тегом в ancestry main. Сохраните major, увеличьте minor на один, установите patch `0`. Например, `1.0.0` становится `1.1.0`, `1.4.3` — `1.5.0`. Несовпадение версии или занятые release-ветка/тег требуют выяснения до записи данных; не выбирайте другую версию молча.

## 2. Feature и каталог

1. Прочитайте [инструкцию каталога](references/catalogue.md). Получите полный список PNG и проверьте оба варианта каждого дизайна. При недоступном CDN, неполных парах или изменении исходников во время подготовки остановите выпуск.
2. Сравните рабочий Firestore с snapshot в Git по содержимому существующих записей. Посторонние изменения требуют согласования; не включайте их в PR новой коллекции.
3. Создайте `feature/add-<number-and-name>` от зафиксированного актуального `origin/development`, сохранив номер папки и ведущие нули. Не перезаписывайте существующую ветку.
4. Просмотрите desktop и mobile изображения, подготовьте manifest с названиями, описаниями, категориями и тегами на четырёх языках в стиле Want. Сначала добавьте необходимые переводы новых тегов или категорий в `src/data/catalog.ts`.
5. Выполните `bun run catalog:add /absolute/path/collection.json --dry-run`. Для рабочего импорта требуйте внешний сервисный ключ, отсутствие `FIRESTORE_EMULATOR_HOST` и проект `want-wallpapers`. При отсутствии доступа подготовьте manifest и дайте инструкцию README; продолжайте после настройки. Не открывайте Firebase Console через браузер без отдельного разрешения.
6. Выполните `bun run catalog:add /absolute/path/collection.json`, подтвердите записи, затем `bun run catalog:pull`. Сверьте count, ID, переводы и snapshot; существующие обои, рейтинги и комментарии сохраняются. Сетевой сбой требует readback до повторного запуска. Не удаляйте данные для восстановления.
7. Добавьте новые collection/detail страницы в проверяемые UI templates и проверку поиска нового дизайна на четырёх языках. Сравнение общего числа карточек используйте из каталога.
8. Выполните команды раздела «Проверки», изучите diff и опубликуйте согласованные изменения через `$delivery-commit-publish`. Для новой ветки установленный `pcoat` может требовать уже существующий remote ref: проверьте реализацию; при таком ограничении сначала опубликуйте исходный development SHA как новую ветку обычным non-force push, задайте её upstream, затем передайте линейные коммиты `pcoat`. Подтвердите HEAD и divergence `0/0`.
9. Создайте PR в `development`. В теле сохраните ID коллекции, исходный URL, рассчитанный release-тег, проверенный feature SHA и результаты проверок. Передайте многострочное тело через `--body-file`; текст и метаданные сохраняйте с нейтральным авторством.
10. Выполните squash с явным сообщением `feat: add <number-and-name> collection` и `--match-head-commit <verified-feature-sha>`. Без admin bypass. Прочитайте PR: `MERGED`, один родитель squash — проверенный development SHA, дерево содержит согласованный кандидат. Если target изменился, пересмотрите diff и проверки.
11. Удалите только эту feature-ветку по разделу «Удаление веток».

## 3. Release в main

1. После fetch создайте `release/v<version>` от подтверждённого `origin/development`. Проверьте весь diff будущего выпуска относительно main: он должен содержать согласованные изменения.
2. Обновите `package.json` и `CHANGELOG.md`: одна версия, фактическая дата выпуска, название коллекции, количество дизайнов и польза для посетителей. Опубликуйте `chore(release): prepare v<version>` через `$delivery-commit-publish` с собственным upstream release-ветки.
3. Выполните проверки на окончательном release-кандидате. Создайте PR в `main`; сохраните в теле ID коллекции, исходный feature PR, версию и release HEAD.
4. Выполните обычный merge с явным сообщением `chore(release): publish v<version>` и `--match-head-commit <verified-release-sha>`. Сохраните два родителя: проверенный прежний main и проверенный release HEAD. Не применяйте squash/rebase или bypass.
5. Подтвердите `MERGED`, родителей, дерево и серверный main SHA. Удалите только эту release-ветку по разделу «Удаление веток».
6. Создайте annotated тег `v<version>` на подтверждённом merge-коммите main с сообщением `Release <version>`. Опубликуйте только этот тег обычным push; через `git ls-remote` проверьте tag object и peeled SHA. Peeled SHA должен совпасть с подтверждённым main. Тег никогда не перемещайте и не удаляйте.

## 4. Обратный merge и GitHub Release

1. В чистом checkout переключитесь на `development` **до** применения `$delivery-semantic-merge`.
2. Примените его с явным источником `origin/main`. Соблюдайте весь skill: `--no-ff --no-commit`, семантическое разрешение конфликтов, `git commit --no-edit`, проверка родителей и ancestry, обычный non-force push и серверный readback. Во время вызова не переключайте ветки; двухродительский merge не публикуйте через `pcoat`.
3. Создайте стабильный GitHub Release на существующем теге через `gh release create` с `--verify-tag --latest --notes-file`. Описание — запись этой версии из changelog. Прочитайте опубликованный Release и сверяйте тег, тело, `draft: false`, `prerelease: false`.
4. Завершите на синхронизированной development. Проверьте refs, `0/0`, наличие main в ancestry development, защищённый тег и отсутствие временных веток. При отсутствии параллельных изменений деревья release-кандидата, main и development совпадают.
5. Сообщите ID и количество обоев, Firebase readback, PR/Release URLs, SHA squash/merge, тег, проверки и ограничения. Разделяйте локальные проверки, CI, серверное состояние и Hosting. Git-релиз не подтверждает деплой или работу Analytics, App Check и рекламы.

## Удаление веток

После readback успешного PR merge сверяйте текущий remote HEAD временной ветки с проверенным PR HEAD. При несовпадении сохраняйте ветку и сообщайте новые коммиты. Перед локальным удалением переключитесь на целевую integration-ветку, синхронизируйте её только через fast-forward и убедитесь, что временная ветка не занята другим worktree и не содержит неопубликованных изменений.

Удаляйте remote ref с проверкой точного SHA, например `git push --force-with-lease=refs/heads/<branch>:<verified-sha> origin --delete <branch>`. Lease здесь защищает удаление проверенного ref; история веток не переписывается. Подтвердите отсутствие через `git ls-remote`. Локальную release-ветку удаляйте через `git branch -d`; feature после squash допускает `-D` только при подтверждённых PR HEAD, локальном/удалённом совпадении и сохранении согласованного дерева в squash. Выполните fetch/prune и проверьте отсутствие tracking ref. Не удаляйте другие feature/release-ветки.

## Проверки

```bash
bun run check
bun test tests/catalog-search.test.ts tests/search-filters.test.ts
firebase emulators:exec --project demo-want-wallpapers --only firestore 'bun test tests/catalog-add.test.ts && bun run test:rules'
bun run build
bun run test:ui
git diff --check
```

Соблюдайте правила запуска браузера из `AGENTS.md`. На новом каталоге проверяйте страницы коллекции и обоев во всех языках, canonical/hreflang, sitemap, описание/alt и structured data, поиск по описанию/тегам, фильтры и оба PNG-скачивания. Новый провал проверки блокирует merge; недоступную проверку сообщайте как непроверенную. Проверяйте реальные required CI checks, если они настроены. После конфликтов повторяйте затронутые проверки.

## Возобновление

- Сначала восстановите этап по серверным документам, PR и Git refs; не повторяйте неоднозначную публикацию вслепую. Восстановите выбранную версию из подтверждённого feature/release PR и changelog, а не увеличивайте уже выпущенную версию ещё раз.
- Если документы полностью совпадают, `catalog:add` возвращает no-op. Если данные частичные или отличаются, остановитесь; не перезаписывайте их и не используйте `catalog:seed`.
- Существующий подходящий PR продолжайте по его точному head/base и состоянию. `MERGED` подтверждайте через API и коммит; удалённую после merge ветку не создавайте заново.
- Существующий annotated тег сверяйте с ожидаемым main merge SHA. Совпадающий тег используйте для оставшихся этапов, несовпадающий — блокер. Если GitHub Release уже есть, проверьте его содержимое, не создавайте дубликат.
- Если коллекция уже выпущена и все этапы подтверждены, сообщите существующий релиз. Если доказательств недостаточно или версия занята другим выпуском, сохраните состояние и уточните конфликт.
