# Prepare a collection

Use one interactive session. Ask for the collection theme and a stable unused collection ID before generation. Read DESIGN.md, the catalogue taxonomy, six canonical locales and docs/ideas/collection-publishing.md. Preparation does not authorize upload, catalogue import, a release or external posts.

Read the installed `wallpaper-concepts`, `wallpaper-pairs` and `telegram-emoji-pack` skills before preparation. Use them in that order. Locate them in the configured skill directories; if one is missing, report it before the affected stage. Keep their responsibilities separate: concepts are text, pairs are finished wallpapers, and the emoji pack contains emoji files. Reuse the agreed theme, count, references and destination instead of repeating answered questions.

Use `wallpaper-concepts` for five distinct proposals. Record the main motif, separate landscape and portrait layouts, palette, lighting and constraints for each. Keep the concept notes and final prompts in the private package directory. Record whether each supplied image is an edit target or a style reference. A revision creates a new sibling directory; preserve the previous package and its approval state.

Create a private directory outside every source checkout with mode 0700. Run `bun run collection init /absolute/private/directory <collection-id> "<theme>"`. Keep files 0600. Never put credentials, private artwork or review pages in Git or public artifacts.

Use `wallpaper-pairs` to prepare five distinct design pairs, ten images total. The collection contract overrides its default portrait ratio and output directory: desktop is 16:9, mobile is 9:16, and all files stay in the private package directory. Generate separate landscape desktop and portrait mobile compositions of each scene using the available interactive image tool and included usage. Do not invoke unattended generation or switch to a paid image API. Save native PNG bytes unchanged. If the aspect ratio differs, extend the composition through an image edit before resizing; retain the native source and extended composition separately. Stop on exhausted included usage. Allow at most two automatic repair passes for the package; record them privately and stop for owner revision after that limit.

Produce ten final PNGs at 3840x2160 and 2160x3840, ten WebP previews at 960x540 and 540x960, and five portrait JPEG social previews at 1080x1920. Use Sharp proportional resizing only after the source has the exact destination ratio. Never crop, stretch or describe enlarged pixels as native 4K.

Use `telegram-emoji-pack` for five distinct transparent static 100x100 PNG emoji motifs, one per design, and retain a separate high-resolution source for each. This count overrides its default. Check the current official Telegram requirements before export. Give every emoji-source asset a name and one Unicode emoji in its `name` and `emoji` fields; media preparation copies them to the final emoji asset so approval binds the mapping. Keep a consistent silhouette weight, light and padding. Inspect every emoji at 100px and 32px on light and dark backgrounds.

Export a private `emoji-pack/` directory with `emoji/`, `source/`, `manifest.json`, `preview-dark.png` and `preview-light.png`, plus a sibling ZIP. The manifest records the checked package hash, names, Unicode values, paths and asset hashes. Derive the pack from validated package bytes; never create a second editable source of metadata. Verify archive membership and byte equality on readback. The review page, previews and archive stay private and do not authorize creation of a Telegram set. Each asset entry records relative path, role, design 1–5, variant when applicable, SHA-256, width and height. Final assets identify their native or composition source; extended compositions identify their native source. Roles are native, composition, final, preview, social, emoji and emoji-source.

Complete package.json schemaVersion 1 with revision, theme, canonical manifest, stories for en/ru/zh-cn/pt-br/ja/ar, assets and English copy for telegram, pinterest, tumblr, deviantart and flickr. Telegram and Tumblr have one post each; other destinations have five. Each post has title and description. Respect the existing licence and required destination classifications.

Run `bun run collection prepare PRIVATE_DIRECTORY` to create derivatives and refresh asset hashes from native/composition and emoji-source entries. The command may extend quantized edges by at most 1% without cropping or changing native bytes, retaining that separate composition. Larger aspect changes require an artwork edit. This increments revision; then run `bun run collection validate PRIVATE_DIRECTORY`, then `bun run collection review PRIVATE_DIRECTORY`. Open only the returned local HTML file. Inspect both variants of every design, original dimensions, enlarged labels, every translation/story, emoji at actual size and destination copy. Correct files before approval, increment revision and repeat validation. Do not change the package after approval.

Ask the owner to approve the exact displayed package hash. Only an explicit approval permits `bun run collection approve PRIVATE_DIRECTORY SHA256`; rejection uses reject with that same hash. No guessed approval or inherited approval from another package. `status` and `resume` revalidate bytes; preparation resumption never publishes. Publication follows the separately authorized local collection publishing path and must revalidate approval immediately before every phase.
